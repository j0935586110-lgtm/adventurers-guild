## Confirmed defects (open)

### E2E-01 — P1: A natural-language task does NOT automatically constrain matchmaking search

Reproduction: Open preview, type "Automate Excel reports for my company. Budget NT$3,000" in the primary task field. Leave "Search keyword" empty. Press "Find real public matches".
Actual: Browser sends GET /api/agentic-directory?mode=all, with no keyword derived from the task text. The UI does not tell the user the brief was not used to rank or filter matches.
Expected: The task text should drive actual matching, or the UI should require and label a separate search keyword without implying automatic intent extraction.
Evidence: browser-e2e.json > briefOnly = {keyword:"",requestUrl:"/api/agentic-directory?mode=all"}; src public/agentic-site.js uses the separate match-keyword field.
Impact: The advertised "tell us your task" journey is not yet a working AI-powered match flow.
Suggested minimal fix: Reuse existing public MCP find_people_and_opportunities intent classification or a narrowly-scoped deterministic keyword extraction with explicit UI confirmation. Do NOT train a model or invent matches.

### E2E-02 — P2: Traditional Chinese shell still renders core browser Agent controls in English

Reproduction: Open preview with ?lang=zh-TW, locate the embedded nsDeploy agent panel.
Actual: Internal UI reads "API key required", "AI model settings", "Developer", provider setup instructions, all in English. The shell is in Traditional Chinese.
Expected: Core onboarding, controls and warnings should follow user-selected language, or have a visible disclaimer that the upstream runtime is currently English-only.
Evidence: Anonymous Chromium DOM text extraction of #agent-app on zh-TW page, 2026-11-19.
Impact: Bilingual experience is incomplete; users may not understand model keys and privacy instructions.
Suggested fix: Check upstream runtime i18n hooks before creating a local translation layer. Do not fork the entire runtime.

### E2E-03 — P2: Choosing English is lost after reload when URL includes lang=zh-TW

Reproduction: Open ?lang=zh-TW, click English. Verify English title, then refresh.
Actual: Language changes to en and localStorage = en; after refresh URL still has ?lang=zh-TW so the site resets to zh-TW and overwrites localStorage.
Expected: A manual language change should persist across refresh OR update the URL language parameter to reflect the selected language.
Evidence: browser-e2e.json > languageSwitch and languageAfterReload.
Suggested fix: Synchronize URL state on language button click, preserving other query parameters, or document explicit URL precedence.

### E2E-04 — P2: Mobile nsDeploy Developer button is positioned beyond viewport

Reproduction: Chrome mobile emulation at 390x844 and 320x720, open the Chinese Agent panel.
Actual: At 390px viewport the Developer button occupies x=491.47..587px, beyond the visible right edge 390px. At 320px it is also off-screen. Body document scrollWidth remains 390 (no full-page horizontal overflow), so this button is not visible in the initial viewport.
Expected: Runtime header controls wrap or remain visible in the available width.
Evidence: browser-e2e.json > mobile.overflowButtons, mobile.debugControl; mobile320.overflowButtons; screenshots mobile-zh.png and mobile320-zh.png.
Suggested fix: Upstream-compatible responsive CSS override for runtime header, verified again at 320, 390 and 1440 widths. No new runtime fork.

### E2E-05 — P3: Browser requests missing favicon.ico

Reproduction: Open preview in a fresh Chromium browser, inspect network.
Actual: GET /favicon.ico returns 404 repeatedly.
Expected: Provide an existing logo as favicon or remove favicon discovery warnings.
Evidence: browser-e2e.json > events.httpErrors (5 repeated favicon 404 entries).
Impact: Cosmetic / unnecessary network errors; not a prize blocker.

## Blocked or not proven (not automatically bugs)

### GATE-01 — P1: Real model -> website tool -> response receipt NOT tested

Browser runtime initializes, but the current anonymous session displays "API key required". No authorized configured model/key was available in the test session, so a real tool invocation and receipt are NOT proven. A mock action response or mere "runtime ready" does not count.
Next: Use an authorized competition-sponsored provider or approved test account, execute read-only search_guild_public_matches and capture actual tool result and human-visible answer.

### GATE-02 — P1: Real member/Agent candidate -> mutual acceptance -> evidence-backed completion NOT tested

Anonymous published Guild data returns HTTP 200, services 0, needs 0, verified agents 0. This is not proof the database is entirely empty. No real counterpart is currently available to make a real match. A preview test cannot claim successful hiring, messaging, delivery or approval.
Next: With real consenting test members, publish one genuine service and one task through existing login/consent flow; inspect public visibility under RLS. Do not insert fabricated production records. Validate private reply / mutual consent in an authorized isolated account.

### GATE-03 — Authenticated publication and full task handoff NOT tested

The first-party brief is preserved in sessionStorage and /matching opens a login dialog in the fresh anonymous profile. Draft input values behind authentication, actual publication, private messages, LINE exchange and completion are untested. This correctly preserves the write-security boundary; do not bypass login for E2E.

### GATE-04 — Peer-to-peer cross-website invocation NOT tested

Published metadata GET and nsDeploy graph validation pass, but no remote website/agent was used to invoke another network. Peer policy remains closed by design; do not interpret metadata CORS as live cross-site interoperability.
